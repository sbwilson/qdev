## Findings

### A. Aggregate views (derived inline over the full range)

**A1 — Deferral without scheduling let two known defects mature into downstream bugs.**
`deferred-work.md` recorded, from the story-1.7 review on 2026-09-08, that (a) `PRAGMA schema_version` was being used as an application version so "any future DDL touch would convert a healthy cache into a destructive full rebuild", and (b) "two files declaring the same frontmatter `id` silently overwrite each other" via `ON CONFLICT(id)`. Both were correctly diagnosed and deferred. Both then caused real defects in later work: (a) is the trap that `create_schema` hit when the cache gained a column (an unmigrated database could be stamped current, then die on every sweep); (b) is the exact root cause of the `--fix-ids` keeper problem, where renumbering the file that owned the cache row made the *kept* id vanish from the cache entirely.
*Source:* `docs/bmad/implementation-artifacts/deferred-work.md` §"Deferred from: code review of spec-1-7"; `crates/qdev-core/src/store/sqlite.rs:593` (`ON CONFLICT(id) DO UPDATE`).
*Disposition:* the two instances are **fixed** in the working tree. The pattern is the finding.

**A2 — `architecture.md` §10 has drifted three tables behind the shipped cache.**
The document describes 13 tables; `ALL_TABLE_NAMES` ships 16. `dirty_entities`, `findings` and `sync_meta` are undocumented, and §11.2 still promises behavior story 1.7 deliberately scoped out. The doc also never states a cache schema version, which is now 3. This was already recorded as deferred work after story 1.7 and has grown staler since (`sync_meta` arrived in 1.12).
*Source:* `docs/architecture.md:245` §10 vs `crates/qdev-core/src/store/sqlite.rs:26` `ALL_TABLE_NAMES`.

### B. Diff-scope review — confirmed defects

Two findings from the adversarial lens over stories 1.1–1.8 were **re-verified against the primary source** by direct reproduction, per the retrospective's rule that sub-agent findings are reports, not facts. Both hold, and both are cross-story defects that no single story's review could have seen.

**B1 — `qdev init` writes a cache that the next command immediately destroys. (CONFIRMED, blocking)**
`init` prints `✔ cache schema v3` and stamps only `PRAGMA user_version`. It never stamps `PRAGMA schema_version`, which SQLite auto-increments once per DDL statement — so a freshly initialised cache carries `user_version=3, schema_version=16` (16 `CREATE TABLE`s). `inspect_cache_schema` requires *both* to equal 3, declares the cache invalid, and the next command takes the write lock, drops every table and rebuilds.

*Reproduction:* `qdev init` in a clean directory, then read the pragmas → `user_version=3 schema_version=16`. Planting a marker table into the post-init cache and running any command destroys it (`probe_marker survived: False`). This is also what the ~150 ms "cold hydration" measured in the behavior check actually was — a forced rebuild, not a first sweep.

*Root cause, and why it is a seam defect:* story 1.3 (`init.rs:390-418`) hand-rolls the pragma write; story 1.6 (`inspect_cache_schema`) defines validity over both pragmas. Each is self-consistent; the contract between them was never checked, and no test asserts `init` → `inspect_cache_schema == Valid`. The underlying misuse — treating SQLite's schema cookie as an application version — was already recorded in `deferred-work.md` after story 1.7 as a latent risk.
*Source:* `crates/qdev-core/src/init.rs:390-418`; `crates/qdev-core/src/store/sqlite.rs:3442-3461`; `deferred-work.md` §spec-1-7.
*Disposition:* **fix now.** Every workspace pays a silent full rebuild on bootstrap, and `init`'s success message is untrue when printed.

**B2 — A write followed by a delete leaves a permanent ghost entity. (CONFIRMED, blocking)**
Story 1.8's write path deletes the entity's `sync_state` row to invalidate it (`write.rs:986-994`). Story 1.7's purge discovers removed files *only* by finding paths present in `sync_state` and absent on disk (`sqlite.rs:3073-3079`). An entity that is written and then deleted therefore has no `sync_state` row, is never purged, and stays queryable forever.

*Reproduction, with a control:*

| Case | Sequence | Cache after sweep |
|---|---|---|
| A (control) | create → hydrate → delete file | **purged correctly** |
| B | create → hydrate → `qdev update` → delete file | **entity survives** |

In a workspace with zero files on disk, `qdev get story E1S1 --json` still returned a complete projection.
*Source:* `crates/qdev-core/src/write.rs:986-994` vs `crates/qdev-core/src/store/sqlite.rs:3073-3079`.
*Disposition:* **FIXED in this retrospective** (Simon's direction). Purge is now driven from the union of `sync_state` and every `entities.source_path`, so a path the cache knows about is purged whether or not the write path invalidated its sync row. Regression test: `sweep_tests.rs::test_entity_written_then_deleted_is_still_purged`. Re-verified end to end — `create → hydrate → update → delete → sync` now leaves the cache with only the surviving story.

*Incidental confirmation:* both cases reported `purged: 0` from `qdev sync` even in case A where a purge did occur — the boot sweep absorbs the work before `handle_sync` runs, exactly as recorded in `deferred-work.md` §spec-1-12. That deferred item is real and still open.

### C. Further confirmed defects (verification-gap and duplication lenses)

Each was re-verified by reproduction against the release binary. All four are cross-story seam defects.

**C1 — A non-default `[storage]` block silently discards every created story. (CONFIRMED, blocking)**
Stories 1.6/1.7 thread `StorageConfig` through the sweep, hydration and validation. Stories 1.3 and 1.5 hardcode the same paths as string literals. With `specs_dir = "planning/specs"` configured:

```
qdev create story E12  →  exit 0, reports "docs/specs/stories/E12S1.md"   (the DEFAULT path)
qdev list stories      →  items: []                                        (reads the CONFIGURED path)
```

The entity is written, the command succeeds, and no read command can ever see it. Two caches also coexist (`.qdev/cache` from `init`, `.qdev/altcache` from boot), and `.gitignore` covers only the first — so the live cache would be committed.
*Source:* `crates/qdev-core/src/init.rs:11-31`, `crates/qdev-core/src/id.rs:448,614,631`, `crates/qdev-cli/src/main.rs:787` vs `crates/qdev-core/src/store/sqlite.rs:2903-2911`.
*Disposition:* **data-loss half FIXED in this retrospective** (Simon's direction). `handle_create_story` now writes into `storage.specs_dir` and allocates through the new `allocate_next_story_id_in`, which scans the configured directory. Regression test: `create_cli_tests.rs::test_create_story_honours_configured_specs_dir`, which pins the path, readability through the cache, and that a second create yields `E12S2` rather than restarting at 1. Re-verified end to end.

**Still open from C1:** `.gitignore` is written by `init` from the *default* layout, so a `cache_dir` changed afterwards is not gitignored and the live cache would be committed. `init` necessarily runs before any config exists, so this needs its own decision (see action item 4 and open question 2) rather than a patch here.

**C2 — `qdev create story` interpolates identity and flags into YAML unescaped. (CONFIRMED)**
`title` is escaped via `serde_json::to_string`; `developer_id`, `--appetite` and `--safety-class` are pushed with `format!`. With `--developer 'alice: the dev #1'`, `qdev create story` exits 0 and writes `id: alice: the dev #1`; the next `qdev validate` reports `schema_violation — YAML parse error: mapping values are not allowed in this context at line 7`. The story is created but un-hydratable, so it never enters the cache.
*Source:* `crates/qdev-cli/src/main.rs:801-838`.
*Disposition:* **fix now.**

**C3 — `qdev doctor` cannot see four of the eight validation checks. (CONFIRMED)**
Hydration findings are persisted to the `findings` table; the four checks story 1.11 computes fresh (`find_duplicate_planning_ids`, `find_orphan_deferred_work`, `find_dw_missing_rationale`, `find_unregistered_target_modules`) are built in memory and never persisted. `doctor`'s `finding_count` reads `store.list_findings()`.

```
qdev validate  →  2 findings  (duplicate_planning_id)
qdev doctor    →  finding_count: 0
```

*Source:* `crates/qdev-core/src/validate.rs:224-238` vs `crates/qdev-core/src/doctor.rs:99`.
*Disposition:* **fix now** — the diagnostic command under-reports the defects a user runs it to find.

**C4 — `QDEV_AUTHOR_TYPE`/`QDEV_AUTHOR_ID` are ignored by `qdev create story`. (CONFIRMED)**
Author resolution is implemented three times (`main.rs:1438` `resolve_author`, `:984-1015` inline in `handle_update`, `:801-805` in `handle_create_story`). The third copy reads only `config.identity.developer_id` and hardcodes `type: human`.

```
QDEV_AUTHOR_TYPE=agent QDEV_AUTHOR_ID=claude qdev create story E9  →  created_by: {type: human,  id: simon}
QDEV_AUTHOR_TYPE=agent QDEV_AUTHOR_ID=claude qdev update story E9S1 →  updated_by: {type: agent, id: claude}
```

Attribution is wrong exactly for the agent-driven case the tool exists to serve, against the "Audited Attribution" requirement.
*Source:* `crates/qdev-cli/src/main.rs:801-805,836` vs `:1438-1473`.
*Disposition:* **fix now.**

## Recommendation: where process rationale should live

Simon's question was whether to store session rationale in the database rather than as logs. Agreed on the substance, with one correction that matters architecturally.

**Not in the database.** FR-101 makes the SQLite cache a *rebuildable index*: wiping `.qdev/cache/` must incur zero data loss, and this retrospective verified that property holds byte-for-byte. Anything written only to the database is destroyed by the next `qdev sync --rebuild`. The cache is the wrong home for a durable record by construction.

**In the entity store — Markdown files, indexed by the cache.** qdev already has the right two vehicles, both scheduled in epic 2:

- **`2-6-scratchpads`** — the per-story working ledger. The natural home for "what this session tried, what it abandoned, and why": attributed to the agent, scoped to the story, git-tracked, and already modelled in the cache as `scratchpad_entries`.
- **`2-7-decision-ledger`** — for the durable subset. A choice that constrains later work (as `DEC-` entities) belongs here rather than in a story's scratchpad, because it outlives the story.

That gets what log files cannot: the rationale is attributed (author type and id), versioned, reviewable in a pull request, queryable through `qdev get --expand scratch`, and survives a cache wipe because the Markdown is the source of truth.

**What this retrospective could not do for want of it.** No session records exist for the 13 story runs, so every process finding here is inferred from commits, specs and triage logs. A1 — the two deferred items that went on to cause both blocking defects — is visible only because `deferred-work.md` happened to record them. Nothing explains *why* they were deferred rather than scheduled, which is the question a retrospective most wants answered.

Worth considering for epic 2: the scratchpad entry is written during the run, not reconstructed afterwards.
